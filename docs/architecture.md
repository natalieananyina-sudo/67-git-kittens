# Архитектура

## Компоненты

```
Браузер врача
  │  React-приложение (Vite): вход, режимы «Один пациент» / «Много пациентов», результат
  │  JSON и загрузка файлов; токен врача в заголовке Authorization
  ▼
nginx (в Docker) или прокси Vite (при разработке)
  │  /api, /docs, /openapi.json → бэкенд; остальное → собранный фронтенд
  ▼
Бэкенд FastAPI (Python)
  ├─ app/routers/     HTTP-эндпоинты, проверка токена, единый формат ошибок
  ├─ app/engine/      всё, что вокруг модели, без привязки к HTTP
  │   ├─ batch.py         чтение CSV/XLSX и проверка формата (файл → строки → ячейки)
  │   ├─ validation.py    проверка записи значений и перевод единиц в единицы датасета
  │   ├─ predictor.py     вызов ML-модуля (и демо-резерв), проверка SHA-256 модели
  │   ├─ pipeline.py      сборка ответа: ответ модуля + подписи + отметки показателей + заключения
  │   ├─ conclusions.py   тексты для врача и для пациента по решению модели
  │   └─ labels.py        русские подписи значений модели
  └─ ml/              ML-модуль ML-команды (без изменений)
      ├─ src/ml/          AnemiaInferenceService: проверка данных, правило анемии, модель, postprocessing
      └─ artifacts/models/final/   pipeline.joblib (модель) и model_manifest.json (паспорт)
```

Логика решения целиком находится в `ml/`, логика представления — в `app/engine/`. Их можно развивать
независимо: новая версия модели подключается заменой папки `ml/`.

## Место сервиса в репозитории

Сервис — это `backend/`, `frontend/`, `config/`, `scripts/`, `docker-compose.yml` и `data/demo/`.
Исследовательская часть (`notebooks/`, `src/preprocess.py`, `src/train.py`, `data/raw|processed|external`,
`models/`, `reports/`) сервисом не импортируется и на его работу не влияет: результат исследований попадает
в сервис только как готовый ML-модуль в `backend/ml`. Ранний прототип `src/anemia-screening/` — отдельное
приложение со своим Docker Compose (порт 8787), с сервисом не связано.

```
notebooks/ + src/  ──(ML-команда: эксперименты → финальная модель)──►  backend/ml  ──►  сервис
```

## Путь одного запроса

1. Врач загружает файл (или вводит показатели). Фронтенд проверяет расширение и размер и отправляет файл
   на `POST /api/v1/screening/file` (один пациент) или `POST /api/v1/screening/batch` (много пациентов).
2. `batch.py` читает таблицу, определяет назначение каждого столбца (ID, пол, возраст, показатель, единица
   в заголовке), отклоняет файл при фатальных проблемах и проверяет каждую ячейку.
3. `validation.py` переводит значения в единицы датасета и проверяет их правдоподобность.
4. `predictor.py` передаёт корректные строки в `AnemiaInferenceService` (для файла — одним вызовом леса).
   Модуль возвращает `status`, `anemia`, `deficiency_cause`, `anemia_class`, `missing_panels` и scores.
5. `pipeline.py` кладёт ответ модуля без изменений в `ml_result`, добавляет русские подписи, отметки
   «ниже/выше нормы» и заключения `conclusions.py` для врача и пациента.
6. Ответ — JSON: результат(ы) и отчёт `file_check` о проверке формата. Данные пациентов нигде не сохраняются.

## Почему так

* **FastAPI** — Python, как у ML-части команды: модуль подключается обычным импортом, без отдельного сервиса.
  Схемы Pydantic проверяют вход и автоматически дают документацию Swagger (`/docs`).
* **Модуль ML-команды без изменений** — одна точка правды для медицинского решения; бэкенд не может
  разойтись с моделью в правиле анемии или в сопоставлении классов.
* **React + Vite** — интерфейс как набор компонентов (`FileDrop`, `FileCheckPanel`, `ResultView`),
  которые переиспользуются в обоих режимах.
* **Docker Compose** — воспроизводимый запуск одной командой; образ бэкенда на Python 3.12, как у модели.

## Производительность

Модель загружается при старте бэкенда (несколько секунд). Один пациент — около 0,1–0,2 с.
Файл: лес вызывается один раз на все строки; 600 пациентов — 10–15 с, весь исходный датасет (840) — около 17 с
на слабой машине. Лимиты одной загрузки: 5 МБ и 1000 строк (`backend/app/config.py`).
