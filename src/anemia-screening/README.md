# Лабораторный скрининг дефицитных состояний

Учебный прототип для кейса Сеченовского университета. Работает с одной записью или CSV. Результат не является диагнозом и не предназначен для клинического применения без проверки на независимых реальных данных и согласования лабораторных единиц, клинических правил и порядка обработки персональных данных.

## Как устроено

| Часть | Выбор | Почему |
| --- | --- | --- |
| Интерфейс | React / TypeScript | Одна форма, пакетный ввод и два варианта отчёта |
| API | Django + Gunicorn | Одна точка для формы, CSV и будущей интеграции; расчёт выполняется на Python |
| Маршрутизация | Nginx | Открывает один локальный адрес и отправляет `/api/` в Django, остальные запросы — в интерфейс |
| Наличие анемии | правило по гемоглобину | Задано в кейсе и однозначно вычисляется |
| Причина | многоклассовая логистическая регрессия | Маленький набор (840 строк), воспроизводимая и переносимая модель |
| Обучение | Python, pandas, scikit-learn | Разделение train/test, метрики, экспорт коэффициентов в JSON |
| Хранение | отсутствует | Для демонстрации нет учётных записей и истории пациентов |
| Генерация текста | шаблоны | Не нужны LLM и передача анализов внешнему провайдеру |

Django читает сохранённые коэффициенты из `lib/model.json`; библиотека scikit-learn нужна при обучении, а не при запуске сервиса. В браузер коэффициенты не передаются. Ни исходный CSV, ни записи пациентов не входят в архив проекта.

## Локальный запуск

`Docker Compose` (рекомендуемый способ для команды):

```bash
docker compose up --build
```

Откройте `http://localhost:8787`. Остановить: `docker compose down`.
Архив сначала нужно распаковать, затем выполнить команду в каталоге
`anemia-screening`. Compose поднимает три контейнера: React интерфейс, Django API и Nginx. Docker собирает образы из исходного кода и уже сохранённой модели. Исходный медицинский CSV в образ не попадает. По умолчанию порт доступен только на компьютере, где запущен Docker; Django снаружи не опубликован.

Без Docker можно запустить API отдельно:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r backend/requirements.txt
cd backend
python manage.py runserver 127.0.0.1:8000
```

Запрос к API в этом режиме отправляйте на `http://127.0.0.1:8000/api/analyze`. Для интерфейса одновременно нужен React (`npm ci`, `npm run dev`) и локальный обратный прокси с маршрутом `/api/` на Django; самый простой полный запуск — `docker compose up --build`. Для переобучения модели нужны Python,
pandas, NumPy и scikit-learn; учебный CSV передаётся скрипту отдельно и не
включён в архив исходного кода.

## Контракт API

`POST /api/analyze` принимает JSON с `sex` (`F` или `M`), `age_years`, `hemoglobin` (г/л) и необязательными признаками из `lib/fields.ts`. Возвращает `result`: `anemia`, `threshold`, `status`, `classCode`, `className`, `measuredMarkers`, `note`. Если профильных маркеров менее двух, `status=insufficient_data` и причина не предсказывается.

Для пакета: `POST /api/analyze` с `{"records":[{...},{...}]}` (1–1000 записей). Ответ `results` содержит результат или ошибку для каждой строки. CSV разбирается в браузере: до отправки остаются только разрешённые признаки и пол; `patient_id`, ФИО и готовые метки не передаются. Сам API принимает произвольный JSON: интеграция должна отправлять только нужные поля и удалять идентификаторы до вызова. Сервер не сохраняет запросы и выставляет `Cache-Control: no-store`. Пример:

```bash
curl -X POST http://localhost:8787/api/analyze -H 'Content-Type: application/json' \
  -d '{"sex":"F","age_years":35,"hemoglobin":115,"ferritin":10,"CRP":2}'
```

Операционные журналы хостинга и реальную обработку медицинских данных нужно проверить отдельно перед запуском. В прототипе API без учётных записей и сеансов, а защита Django от CSRF для него отключена; при добавлении входа пользователей необходимо пересмотреть авторизацию и CSRF.

## Обучение и проверка

```bash
python ml/train.py /path/to/deficiency_anemia.csv
```

Скрипт откладывает 20% пациентов с сохранением пропорций 12 классов (`random_state=42`), считает accuracy, macro F1 и метрики классов, затем обучает итоговую модель на всех 840 строках. Медианы и масштаб вычисляются только на обучающей части проверки. Пропуски представлены также отдельными бинарными признаками. `patient_id` и целевые колонки исключены.

Результат проверки модели: accuracy 0.8393 и macro F1 0.8443 на 168 строках; подробности в `lib/evaluation.json`. Дополнительное правило сервиса не выводит причину, когда профильных показателей меньше двух или класс противоречит порогу гемоглобина: на отложенных данных это 4 из 168 строк, среди оставшихся 164 точность 0.8476. Это оценка на частично синтетической таблице. Вероятности не калиброваны, поэтому сервис не показывает их как медицинскую уверенность. Классы смешанного дефицита и дефицита меди распознаются хуже. Внешняя клиническая валидация ещё не проведена.

## Что нужно перед реальным внедрением

1. Получить описание единиц и референсов каждого показателя; добавить явное преобразование единиц и проверку допустимых значений.
2. С врачами согласовать правила интерпретации, сценарии недостаточных данных и рекомендации по дообследованию.
3. Проверить модель на независимых реальных пациентах и по каждому классу.
4. Утвердить порядок обработки данных, доступ, журналы, хранение и интеграцию. Замена ФИО кодом сама по себе не гарантирует обезличивание.
