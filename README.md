# Скрининг анемий и латентных дефицитных состояний

Команда **Git kittens** (репозиторий `67-git-kittens`), кейс Сеченовского университета.

Веб-сервис поддержки врачебного решения. По числовым результатам лабораторных анализов он определяет наличие
анемии, выявляет признаки скрытых (латентных) дефицитных состояний и формирует заключение в двух версиях —
для врача и для пациента. Решение принимает обученная ML-модель команды (Hierarchical Random Forest + panel masking).

> Сервис выполняет скрининг и не ставит диагноз, не назначает лечение. Окончательное решение принимает врач.
> Реальные персональные данные не используются: только псевдонимизированный ID случая.

## Цели и задачи

**Цель** — сократить число пропущенных и неверно интерпретированных дефицитных состояний. Если смотреть на
показатели по отдельности, легко ошибиться: воспаление маскирует дефицит железа, сочетанные дефициты
«нормализуют» MCV, пограничный B12 требует функционального подтверждения.

**Задачи:**

1. Принимать лабораторные данные одного или многих пациентов (CSV, XLSX, ручной ввод) и проверять их формат.
2. Приводить показатели к единицам исходного датасета.
3. Определять анемию по клиническому правилу (Hb < 120 г/л у женщин, < 130 г/л у мужчин).
4. Определять причину (`deficiency\_cause`) и итоговый класс (`anemia\_class`, 12 классов) с помощью ML-модели;
честно сообщать, когда данных для вывода недостаточно.
5. Давать рекомендации по дообследованию: подробно для врача, понятным языком для пациента.

## Как устроено

```
Браузер (React) ──► FastAPI ──► проверка формата и единиц ──► ML-модуль (backend/ml) ──► заключения ──► ответ
                                (backend/app/engine)          AnemiaInferenceService      (тексты эксперта)
```

Разделение ответственности согласовано с ML-командой (см. [backend/ml/README\_ML.md](backend/ml/README_ML.md)):

* **ML-модуль** (`backend/ml/src/ml`, передан ML-командой и не изменяется) делает все, что относится к решению:
проверку достаточности данных, правило анемии, preprocessing, модель, ограничение допустимых причин
(constrained postprocessing) и итоговый `anemia\_class`.
* **Бэкенд** этого не дублирует. Он читает и проверяет файлы, переводит единицы, передает данные в модуль,
а ответ модуля без изменений кладет в поле `ml\_result` и дополняет русскими подписями и заключениями.

Подробнее: [docs/architecture.md](docs/architecture.md), [docs/ml\_integration.md](docs/ml_integration.md).

готовый артефакт в `backend/ml`.

## Развертывание и запуск

Есть два независимых способа запуска, и у каждого свой адрес:

|Способ|Для чего|Адрес|
|-|-|-|
|Docker (`docker compose up`)|демонстрация, проверка «как на сервере»|http://localhost:8080|
|Скрипты (`scripts/dev.sh`)|разработка: правки кода видны сразу|http://localhost:5173|

Адрес работает, только пока запущен соответствующий способ: при запуске через Docker порт 5173
не открыт, при запуске через `scripts/dev.sh` не открыт порт 8080.

### Вариант 1. Docker (рекомендуется)

Требуется Docker Desktop (Windows/macOS) или Docker Engine с Compose (Linux).

```bash
docker compose up --build
```

Откройте http://localhost:8080. Документация API: http://localhost:8080/docs. Первая сборка занимает
несколько минут; после старта бэкенду нужно еще несколько секунд на загрузку модели. Остановка: `Ctrl+C`,
затем `docker compose down`.

### Вариант 2. Без Docker (Linux, macOS, WSL)

Требуется Python 3.11+ (рекомендуется **3.12** — на нем ML-команда сохранила модель) и Node.js 20.19+ (или 22.12+).

```bash
scripts/setup.sh    # один раз: окружение Python, зависимости, smoke-test модели, зависимости фронтенда
scripts/dev.sh      # бэкенд (порт 8000) и фронтенд (порт 5173) вместе; остановка Ctrl+C
```

Откройте http://localhost:5173. Вручную то же самое — в двух терминалах:

```bash
# терминал 1
cd backend \&\& python3.12 -m venv .venv \&\& source .venv/bin/activate
pip install -r requirements-dev.txt          # включает точные версии ML-зависимостей из ml/requirements-ml.txt
uvicorn app.main:app --reload --port 8000

# терминал 2
cd frontend \&\& npm ci \&\& npm run dev
```

Зависимости ML-модуля зафиксированы ML-командой (`scikit-learn==1.9.0`, `pandas==3.0.3`, `numpy==2.4.6`,
`joblib==1.5.3`) и подключаются в `backend/requirements.txt` строкой `-r ml/requirements-ml.txt`. Менять их не
следует: модель сохранена этими версиями.

### Проверки

```bash
cd backend/ml \&\& ../.venv/bin/python example\_inference.py   # smoke-test модели из поставки ML-команды
scripts/test.sh     # smoke-test модели + pytest + линтер и сборка фронтенда
```

`pytest` запускает 83 теста сервиса и 9 тестов исследовательской части (`tests/test\_preprocess.py`).
Последние пропускаются, если нет `data/processed/df\_features.csv` (файл создает `notebooks/02\_features.ipynb`).

### Исследовательская часть (ноутбуки)

Для сервиса не нужна. Полное окружение ставится из корневого `requirements.txt`: он подключает зависимости
сервиса с точными версиями ML-библиотек и добавляет библиотеки для ноутбуков (matplotlib, seaborn, xgboost,
lightgbm, imbalanced-learn, shap, jupyter).

```bash
python3.12 -m venv .venv \&\& source .venv/bin/activate
pip install -r requirements.txt
cp путь/к/deficiency\_anemia.csv data/raw/          # исходный датасет в git не хранится
jupyter notebook notebooks/                        # 01 → 02 (создает data/processed/df\_features.csv) → 03 → 04 → 05
python src/train.py                                # эксперимент RandomForest: models/model.pkl, reports/metrics.json
```

Модели из `src/train.py` и ноутбуков — эксперименты; сервис их не использует. Финальная модель сервиса
(`anemia\_hierarchical\_rf\_masked\_v1`) поставлена ML-командой в `backend/ml` вместе с runtime-кодом.

### Ранний прототип

`src/anemia-screening/` — первый прототип команды (Next.js + Django, логистическая регрессия). Сохранен без
изменений кода, запускается отдельно (`docker compose up --build` в его папке, порт 8787) и с основным
сервисом не связан. Подробнее — в его [README](src/anemia-screening/README.md).

## Использование

1. **Вход:** логин `doctor\_demo`, пароль `y7pr-gHXm-Pb9w`. Работает только эта пара; она задана в
`backend/app/config.py` и может быть переопределена в `config/backend.env`.
2. **Выбор режима** на приветственном экране: «Один пациент» или «Много пациентов». Сменить режим можно

3. **Загрузка файла.** Формат — как в шаблоне (кнопка «Скачать шаблон») и в исходных данных. Ошибки формата
показываются списком с номером строки и названием столбца; строки с ошибками не обрабатываются.
4. **Результат:** вкладки «Для врача» и «Для пациента», печать версии для пациента. Если данных не хватает,
результат будет «Недостаточно данных для заключения» с объяснением, чего именно не хватает.

[docs/demo\_scenario.md](docs/demo_scenario.md).

## Входные и выходные данные, API

* **Вход:** CSV/XLSX или JSON; столбцы `patient\_id`, `age\_years`, `sex`, `hemoglobin` и до 34 других показателей
(названия как в исходном датасете). Полное описание, таблица единиц и допустимых диапазонов —
[docs/data\_format.md](docs/data_format.md).
* **Выход** для каждого пациента:

  * `ml\_result` — ответ ML-модуля без изменений: `status` (`signal\_detected` / `no\_signal\_detected` /
`insufficient\_data`), `reason`, `anemia`, `deficiency\_cause`, `anemia\_class`, `missing\_panels`,
`deficiency\_cause\_scores`, `model\_score`;
  * русские подписи, показатели с отметками «ниже/выше нормы», заключения для врача и пациента,
перечень переведенных единиц; для файлов — отчет о проверке формата.
* **API:** `POST /api/v1/screening` (JSON), `POST /api/v1/screening/file` (один пациент из файла),
`POST /api/v1/screening/batch` (много пациентов). Подробно — [docs/api.md](docs/api.md) и Swagger `/docs`.

## Ограничения и особенности медицинской тематики

* **Скрининг, а не диагноз.** Результат — поддержка решения врача; формулировки «предварительное заключение»,
«рекомендуется обсудить с врачом». Лечение и дозировки не назначаются (блок с лечением из заключений эксперта
скрыт; включается `INCLUDE\_TREATMENT\_HINTS=true` в `config/backend.env` по решению команды).
* **Качество модели.** На отложенной test-выборке: macro-F1 0,88, balanced accuracy 0,88 (паспорт модели).
Модель обучена на этом же датасете, поэтому на демо-наборах (созданных из него) совпадение выше — до 98 %
среди достаточных строк; это не оценка качества. Исходные данные частично синтетические: метрики не переносятся
автоматически на реальную клинику. Модель — прототип, не валидированная медицинская система.
* **Оценки модели — не вероятности.** `model\_score` и `deficiency\_cause\_scores` — технические scores для сравнения
вариантов между собой. Интерфейс не показывает их в процентах и не называет «вероятностью диагноза».
* **Недостаточно данных.** Модель не делает вывод, если не указан пол или гемоглобин либо полностью отсутствуют
две и более панели анализов (кроме общего анализа крови). В исходных данных таких строк около трети.
Это решение ML-модуля; сервис показывает его как отдельный результат и перечисляет недостающие панели.
* **Анемия без выявленного дефицита** не называется «анемией иной природы»: формулировка — «требуется дальнейшая
клиническая дифференциальная оценка».
* **Возраст** — только взрослые (от 18 лет); референсные интервалы на экране ориентировочные и в модель не передаются.
* **Единицы.** Значение вне правдоподобного диапазона отклоняется с подсказкой проверить единицы
(типичная ошибка — гемоглобин в г/дл вместо г/л).
* **Целостность модели.** Перед загрузкой сервис сверяет SHA-256 файла модели с паспортом. Если модель не
загрузилась, в режиме `ML\_MODE=auto` включается демо-резерв с заметным предупреждением в интерфейсе;
в режиме `ML\_MODE=model` сервис не запускается.

## Персональные данные и безопасность

* Принимается только псевдонимизированный ID; файлы со столбцами ФИО, контактов, документов и даты рождения
отклоняются. Данные пациентов не сохраняются ни на сервере, ни в браузере; ответы API не кэшируются.
* Все эндпоинты скрининга требуют токен врача; пароль сравнивается в постоянное время, перебор ограничен.
* MVP не заявляется как полностью соответствующий 152-ФЗ: промышленное внедрение потребует отдельной
проработки правовых, организационных и технических мер.
