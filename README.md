# Скрининг анемий и латентных дефицитных состояний

Команда **Git kittens**, репозиторий `67-git-kittens`.

MVP представляет собой веб-сервис для первичного скрининга анемий и связанных дефицитных состояний по результатам лабораторных исследований. Основной пользователь — медицинский специалист. Сервис принимает данные одного пациента или группы пациентов, валидирует входные значения, приводит поддерживаемые единицы измерения к единому формату, выполняет анализ и формирует два представления результата: профессиональное для врача и понятное для пациента.

## Цель и задачи решения

**Цель** — автоматизировать первичный анализ лабораторных данных при скрининге анемий и дефицитных состояний и предоставить врачу структурированный результат для дальнейшей клинической оценки.

В рамках MVP решены следующие задачи:

- прием данных одного пациента вручную, из CSV/XLSX или через REST API;
- пакетная обработка CSV/XLSX с несколькими пациентами;
- проверка структуры файлов, типов данных, допустимых диапазонов и единиц измерения;
- определение наличия анемии по клиническому правилу: Hb < 120 г/л для женщин и Hb < 130 г/л для мужчин;
- определение предполагаемой причины и итогового класса состояния с помощью ML-модуля;
- обработка неполных данных с отдельным статусом `insufficient_data`;
- формирование заключения для врача и пациентской версии результата;
- предоставление REST API для использования screening engine отдельно от веб-интерфейса.

## Что реализовано

| Компонент | Реализация |
| --- | --- |
| Авторизация | Демо-учетная запись врача, JWT-токен, ограничение числа неудачных попыток входа |
| Один пациент | Загрузка CSV/XLSX с одной строкой или ручной ввод лабораторных показателей |
| Пакетный анализ | Загрузка CSV/XLSX до 1000 строк, сводная таблица и просмотр результата отдельного случая |
| Валидация | Проверка обязательных столбцов, формата значений, диапазонов, персональных данных и единиц измерения |
| Единицы измерения | Автоматическое преобразование поддерживаемых альтернативных единиц в стандартные |
| ML-модуль | `anemia_hierarchical_rf_masked_v1`, Random Forest с panel masking; версия модели `1.0.0` |
| Результат | Статус скрининга, анемия, предполагаемая причина, итоговый класс, отсутствующие панели, лабораторные показатели и заключения |
| Представление результата | Отдельные вкладки «Для врача» и «Для пациента», печать пациентской версии |
| API | FastAPI, REST API, OpenAPI/Swagger |
| Развертывание | Docker Compose; отдельные Docker-образы backend и frontend |
| Тестовые данные | Демо-наборы для одиночного и пакетного анализа |

Финальная ML-модель имеет `macro-F1 = 0.8835` и `balanced accuracy = 0.8768` на отложенной тестовой выборке согласно паспорту модели `backend/ml/artifacts/models/final/model_manifest.json`.

## Архитектура

```text
Браузер врача
    │
    ▼
React + Vite
    │
    ▼
nginx / Vite proxy
    │
    ▼
FastAPI backend
    │
    ├── проверка файла и входных значений
    ├── преобразование единиц измерения
    │
    ▼
ML-модуль backend/ml
    ├── проверка достаточности данных
    ├── клиническое правило определения анемии
    ├── ML-оценка предполагаемой причины
    └── формирование итогового anemia_class
    │
    ▼
Backend: подписи, лабораторные флаги и заключения
    │
    ▼
Результат для врача / результат для пациента
```

Фронтенд не содержит медицинской логики. Он отвечает за ввод данных, загрузку файлов и отображение ответа API.

Backend выполняет валидацию и подготовку входных данных, вызывает ML-модуль и формирует пользовательское представление результата. Медицинское решение не дублируется в backend: `ml_result` возвращает результат ML-модуля без изменения его класса и причины.

### ML-логика

Модель разделяет детерминированную и ML-часть анализа:

1. Достаточность данных проверяется внутри ML-модуля.
2. Наличие анемии определяется клиническим правилом по полу и гемоглобину.
3. `RandomForestClassifier` определяет предполагаемую причину (`deficiency_cause`) среди допустимых для конкретного состояния вариантов.
4. Итоговый `anemia_class` формируется из результата определения анемии и предполагаемой причины.

Технические поля `model_score` и `deficiency_cause_scores` используются для сравнения вариантов внутри модели и не являются клинически откалиброванными вероятностями диагноза.

## Развертывание и запуск

### Вариант 1. Docker Compose

Рекомендуемый способ запуска для демонстрации и проверки решения.

**Требования:**

- Docker Desktop для Windows/macOS или Docker Engine для Linux;
- Docker Compose v2.

Из корня репозитория выполните:

```bash
docker compose up --build
```

После завершения сборки:

- веб-интерфейс: `http://localhost:8080`;
- Swagger/OpenAPI: `http://localhost:8080/docs`;
- health-check: `http://localhost:8080/api/v1/health`.

Для остановки нажмите `Ctrl+C`, затем выполните:

```bash
docker compose down
```

При запуске через Docker отдельная установка Python- и npm-зависимостей не требуется: они устанавливаются при сборке образов.

### Вариант 2. Локальный запуск без Docker

**Требования:**

- Python 3.12;
- Node.js `^20.19.0` или `>=22.12.0`;
- npm.

Backend:

```bash
cd backend
python -m venv .venv
```

Активация окружения:

```powershell
# Windows PowerShell
.venv\Scripts\Activate.ps1
```

```bash
# Linux / macOS / WSL
source .venv/bin/activate
```

Установка зависимостей и запуск:

```bash
pip install -r requirements-dev.txt
uvicorn app.main:app --reload --port 8000
```

В отдельном терминале запустите frontend:

```bash
cd frontend
npm ci
npm run dev
```

После запуска:

- веб-интерфейс: `http://localhost:5173`;
- backend API: `http://localhost:8000`;
- Swagger/OpenAPI: `http://localhost:8000/docs`.

Финальная модель уже включена в `backend/ml`; отдельное обучение модели для запуска сервиса не требуется.

## Использование

### Демо-авторизация

Для входа в MVP используется заранее созданная учетная запись врача:

```text
Логин:  doctor_demo
Пароль: y7pr-gHXm-Pb9w
```

После входа доступны два режима.

### Один пациент

Данные можно передать двумя способами:

1. загрузить CSV/XLSX с одной строкой пациента;
2. ввести данные вручную в интерфейсе.

После обработки отображается индивидуальный результат с переключением между представлениями «Для врача» и «Для пациента».

### Много пациентов

В режиме пакетного анализа загружается CSV/XLSX с несколькими строками. Сервис:

- проверяет структуру и значения файла;
- обрабатывает корректные строки;
- сохраняет ошибочные строки в отчете с указанием строки и столбца;
- выводит сводную таблицу результатов;
- позволяет открыть полный результат отдельного пациента.

Шаблон файла доступен из интерфейса и через API.

## Входные данные

### CSV/XLSX

Поддерживаются:

- CSV с разделителем `,`, `;` или tab;
- кодировки UTF-8 и Windows-1251;
- XLSX, первый лист.

Обязательные столбцы файла:

- `patient_id` или `case_id` — псевдонимизированный ID случая;
- `age_years` или `age` — возраст;
- `sex` — пол;
- `hemoglobin` — гемоглобин.

Дополнительно поддерживаются до 34 других лабораторных показателей. Полный перечень, допустимые диапазоны и единицы приведены в [`docs/data_format.md`](docs/data_format.md).

Пример минимального файла:

```csv
patient_id,age_years,sex,hemoglobin,ferritin,MCV,CRP
P-001,42,F,108,8,74,2.1
```

Единицу можно указать в заголовке, например:

```csv
patient_id,age_years,sex,hemoglobin (g/dL),ferritin (ng/mL)
P-001,42,F,10.8,8
```

Поддерживаемые единицы будут автоматически преобразованы в стандартные.

Ограничения одной загрузки:

- размер файла — до 5 МБ;
- пакетный файл — до 1000 пациентов;
- для режима одного пациента файл должен содержать ровно одну строку данных.

### JSON

Один случай можно передать напрямую в REST API:

```json
{
  "case_id": "A7F4C92",
  "age": 42,
  "sex": "female",
  "laboratory_data": {
    "hemoglobin": 108,
    "MCV": 74,
    "ferritin": 8,
    "CRP": 2.1
  },
  "units": {
    "hemoglobin": "g/L"
  }
}
```

`units` необязателен. Неизвестные допустимые лабораторные показатели можно не передавать.

## Выходные данные

Для одного пациента API возвращает структурированный JSON, включающий:

- `screening_status` — `signal_detected`, `no_signal_detected` или `insufficient_data`;
- `anemia` — результат определения анемии и использованный порог;
- `deficiency_cause` — предполагаемая причина по модели;
- `anemia_class` — итоговый класс состояния;
- `missing_panels` — полностью отсутствующие панели лабораторных данных;
- `model_scores` — технические оценки вариантов модели;
- `labs` — переданные показатели с единицами и отметками относительно ориентировочных референсов;
- `report.doctor` — врачебное представление результата;
- `report.patient` — пациентское представление результата;
- `unit_conversions` — выполненные преобразования единиц измерения;
- `ml_result` — исходный результат ML-модуля.

Сокращенный пример ответа:

```json
{
  "case_id": "A7F4C92",
  "status": "completed",
  "screening_status": "signal_detected",
  "anemia": {
    "detected": true,
    "hemoglobin": 108.0,
    "threshold": 120.0,
    "unit": "г/л"
  },
  "deficiency_cause": "iron_deficiency",
  "anemia_class": "iron_deficiency_anemia",
  "missing_panels": []
}
```

При пакетной обработке API дополнительно возвращает сводку по файлу, результат по каждой строке и отчет о найденных ошибках/предупреждениях.

## REST API

Все рабочие эндпоинты имеют префикс `/api/v1`.

| Метод | Endpoint | Назначение |
| --- | --- | --- |
| `GET` | `/api/v1/health` | Проверка состояния backend и информации о загруженной модели |
| `GET` | `/api/v1/analytes` | Справочник поддерживаемых лабораторных показателей |
| `POST` | `/api/v1/auth/login` | Авторизация врача и получение JWT |
| `GET` | `/api/v1/auth/me` | Информация о текущем пользователе |
| `POST` | `/api/v1/screening` | Анализ одного пациента из JSON |
| `POST` | `/api/v1/screening/file` | Анализ одного пациента из CSV/XLSX |
| `POST` | `/api/v1/screening/batch` | Пакетный анализ CSV/XLSX |
| `GET` | `/api/v1/screening/batch/template` | Шаблон CSV |
| `GET` | `/api/v1/screening/examples` | Демо-примеры одиночных случаев |

Эндпоинты скрининга требуют JWT-токен:

```http
Authorization: Bearer <access_token>
```

Полная интерактивная документация API автоматически формируется FastAPI и доступна по `/docs`.

Дополнительное описание API: [`docs/api.md`](docs/api.md).

## Ограничения и особенности медицинской тематики

- Сервис предназначен для **скрининга и поддержки принятия решения**, а не для постановки окончательного клинического диагноза.
- Сервис не назначает лекарственные препараты, дозировки или лечение. Тактику ведения определяет медицинский специалист.
- Наличие анемии определяется клиническим правилом по уровню гемоглобина и полу; ML используется для оценки предполагаемой причины и итогового класса состояния.
- `model_score` и `deficiency_cause_scores` не являются откалиброванными вероятностями диагноза.
- Модель разработана в рамках хакатонного прототипа и требует отдельной клинической валидации перед применением в реальной медицинской практике.
- Исходный набор данных частично синтетический; метрики тестовой выборки не являются оценкой эффективности на реальной клинической популяции.
- Анализ рассчитан на взрослых пациентов; допустимый возраст во входных данных — 18–120 лет.
- При отсутствии пола, гемоглобина или при недостаточном наборе лабораторных панелей модель возвращает `insufficient_data` вместо итогового класса.
- В демонстрационном контуре используются только псевдонимизированные ID. Файлы со столбцами ФИО, телефона, адреса, СНИЛС, паспортных данных, даты рождения и других прямых идентификаторов отклоняются.
- Данные пациентов не сохраняются приложением между запросами; ответы API с медицинскими данными отправляются с `Cache-Control: no-store`.
- Реальная интеграция с конкретной МИС/ЛИС не выполнена. Для интеграции реализован и документирован REST API.
